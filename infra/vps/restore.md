# Restoring from a backup

`backup.sh` (README §12) writes one folder per night to
`/var/backups/baja/<UTC timestamp>/` while the pipeline stack is up, keeping
the newest 14. A folder named `…-incomplete` had at least one part fail; the
journal says which (`journalctl -u baja-backup.service`).

| File | What | Restore section |
| --- | --- | --- |
| `bvp.sqlite3` | orchestrator jobs DB: every job, review, holder, event, enrolled worker | A |
| `reviewers.txt`, `teams.csv` | reviewer logins (base Caddy + orchestrator), car → team names | B |
| `SHA256SUMS` | checksums of the above | — |

**Not in the backup, on purpose:**

* `.env` and `orchestrator.env`: they hold every secret. Keep a copy in the
  password manager and update it whenever you change one.
* Raws, proxies, thumbnails, clips: the master worker holds every raw
  (design §4, §11), proxies are regenerated by any holder on request, and
  clips are on the streaming PC.
* Evolution (Postgres, Redis, instances volume): the base stack
  (`jbresolin/baja-vps`) backs those up and has the restore steps.

`reviewers.txt` holds password hashes, so a backup folder stays mode 700,
and copies off the VPS go only to machines you control.

Run everything below as root from `/opt/baja/infra/vps`, with the
variables loaded (`set -a; . ./.env; set +a`). Pick the backup first:

```bash
ls -1 /var/backups/baja/
B=/var/backups/baja/<timestamp>          # the one to restore
(cd "$B" && sha256sum -c SHA256SUMS)     # every line must say OK
```

---

## A. The jobs DB (`bvp.sqlite3`)

When: the DB is damaged, or a bad change has to be undone. Everything after
the backup's time is lost (jobs received since then must be re-sent or
re-ingested; workers stay enrolled only if they enrolled before it).

```bash
sudo docker compose stop review-ui orchestrator
sudo setpriv --reuid 10001 --regid 10001 --clear-groups -- \
  python3 /opt/baja/infra/vps/sqlite_backup.py restore "$B/bvp.sqlite3" /srv/pipeline/db/bvp.sqlite3
sudo ./up.sh
```

`stop` (not `down.sh`) keeps the webhook and the public routes in place for
the minute this takes; Evolution retries what it could not deliver. `up.sh`
starts the two containers again and runs the smoke test.

`sqlite_backup.py restore` refuses to run while the orchestrator still
has the DB open (a `bvp.sqlite3-wal` file exists), checks the backup's
integrity before touching anything, and keeps the replaced DB as
`bvp.sqlite3.before-restore`. Running it as uid 10001 keeps the file owned
by the orchestrator's user.

After the restore, workers reconcile on their own: a heartbeat whose
`held_job_ids` lists a job the DB does not know is ignored, and holders the
DB remembers but a worker no longer reports are dropped (design §17). Raws
of jobs that arrived after the backup are still on the holders' disks;
re-send those videos to the bot if they matter.

The pipeline down (between events)? Restore the file the same way with no
`stop` first; the next `./up.sh` starts on it.

## B. Reviewers and teams

```bash
sudo install -o 10001 -g 10001 -m 640 "$B/reviewers.txt" /srv/pipeline/reviewers.txt
sudo install -o 10001 -g 10001 -m 640 "$B/teams.csv" /srv/pipeline/teams.csv
sudo docker exec -w /etc/caddy caddy caddy reload --config /etc/caddy/Caddyfile
```

The orchestrator re-reads both files when they change; no restart. The
reload is for the base Caddy's reviewer basic auth (README §4); skip it if
the pipeline is down.

## C. A new VPS from scratch

1. The base stack first, from its own repo (it restores Evolution).
2. README §1 and §2 (directories, `ip_nonlocal_bind`, inbox mount), then
   put `.env` and `orchestrator.env` back from the password manager, and
   `docker login ghcr.io` if the images are private (README §5).
3. Copy the backup folder over the tailnet:
   `rsync -a <old-or-archive-host>:/var/backups/baja/<timestamp>/ /var/backups/baja/<timestamp>/`
   and check `sha256sum -c SHA256SUMS`.
4. Restore B (without the reload), then A (without the `stop`).
   A new VPS gets a new Tailscale IP, but every worker has the old one in
   `worker.json` (`orchestrator_url`, `tailnet_base_url`). Easiest: delete
   the old machine in the Tailscale admin console, then give the new one
   the old IPv4 (machine menu → *Edit machine IPv4*). Otherwise set the new
   `TAILSCALE_IP` in `.env` and edit both URLs in each worker's `worker.json`.
5. `sudo ./up.sh` (containers, routes, webhook, smoke test).

## Keeping a copy off the VPS

The backups sit on the same disk as what they protect. Pull them to a
machine you control after the nightly run, over the tailnet (an admin
device may SSH to `tag:server`, `infra/tailnet/acl.hujson`), e.g. from
TrueNAS or João's desktop:

```bash
rsync -a --delete root@<vps-tailscale-ip>:/var/backups/baja/ /mnt/tank/backups/baja-vps/
```

## Practising a restore

Do drill A once before each event (EVENT_DAY.md, T-7) on a copy, without
stopping anything:

```bash
python3 /opt/baja/infra/vps/sqlite_backup.py restore "$B/bvp.sqlite3" /tmp/drill/bvp.sqlite3   # mkdir -p /tmp/drill first
rm -rf /tmp/drill
```

It prints the job count of the backup; it should match roughly what the
fleet page showed the night before.
