# Restoring from a backup

`backup.sh` (README §13) writes one folder per night to
`/var/backups/baja/<UTC timestamp>/`, keeping the newest 14. A folder named
`…-incomplete` had at least one part fail; the journal says which
(`journalctl -u baja-backup.service`).

| File | What | Restore section |
| --- | --- | --- |
| `bvp.sqlite3` | orchestrator jobs DB: every job, review, holder, event, enrolled worker | A |
| `reviewers.txt`, `teams.csv` | reviewer logins (Caddy + orchestrator), car → team names | B |
| `evolution.dump` | Evolution's Postgres (instance row, `Session` creds, webhook config, messages) | C |
| `evolution.rdb` | Evolution's Redis (the WhatsApp Signal keys) | C |
| `evolution_instances.tgz` | Evolution's instances volume | C |
| `SHA256SUMS` | checksums of the above | — |

**Not in the backup, on purpose:**

* `.env` and `orchestrator.env`: they hold every secret. Keep a copy in the
  password manager and update it whenever you change one.
* Raws, proxies, thumbnails, clips: the master worker holds every raw
  (design §4, §11), proxies are regenerated by any holder on request, and
  clips are on the streaming PC.

The Evolution files contain the WhatsApp session keys. Treat a backup
folder like a password: it stays mode 700, and copies off the VPS go only
to machines you control.

Run everything below as root from `/opt/baja/infra/vps`, with the
variables loaded (`set -a; . ./.env; set +a`). Pick the backup first:

```bash
ls -1 /var/backups/baja/
B=/var/backups/baja/<timestamp>          # the one to restore
(cd "$B" && sha256sum -c SHA256SUMS)     # every line must say OK
```

---

## A. The jobs DB (`bvp.sqlite3`)

When: the DB is damaged, or a bad change has to be undone. Everything after
the backup's time is lost (jobs received since then must be re-sent or
re-ingested; workers stay enrolled only if they enrolled before it).

```bash
sudo docker compose --profile orchestrator stop review-ui orchestrator
sudo setpriv --reuid 10001 --regid 10001 --clear-groups -- \
  python3 /opt/baja/infra/vps/sqlite_backup.py restore "$B/bvp.sqlite3" /srv/pipeline/db/bvp.sqlite3
sudo docker compose --profile orchestrator up -d orchestrator review-ui
sudo ./compose-smoke.sh
```

`sqlite_backup.py restore` refuses to run while the orchestrator still
has the DB open (a `bvp.sqlite3-wal` file exists), checks the backup's
integrity before touching anything, and keeps the replaced DB as
`bvp.sqlite3.before-restore`. Running it as uid 10001 keeps the file owned
by the orchestrator's user.

After the restore, workers reconcile on their own: a heartbeat whose
`held_job_ids` lists a job the DB does not know is ignored, and holders the
DB remembers but a worker no longer reports are dropped (design §17). Raws
of jobs that arrived after the backup are still on the holders' disks;
re-send those videos to the bot if they matter.

## B. Reviewers and teams

```bash
sudo install -o 10001 -g 10001 -m 640 "$B/reviewers.txt" /srv/pipeline/reviewers.txt
sudo install -o 10001 -g 10001 -m 640 "$B/teams.csv" /srv/pipeline/teams.csv
sudo docker compose exec caddy caddy reload --config /etc/caddy/Caddyfile
```

The orchestrator re-reads both files when they change; no restart.

## C. Evolution (Postgres + Redis + instances)

When: Evolution's data is lost or damaged **on this VPS**. These are the
same three stores the migration copied (README §3.2), restored the same
way (README §3.4–§3.6), except that the containers already exist.

> Golden rule (README §0): never run two Evolutions with the same session,
> and never call logout/delete. If Evolution is merely disconnected, read
> README §4 first; restoring is not a fix for a `close` state.

```bash
sudo docker compose stop evolution

# Postgres: replace Evolution's tables with the dump's.
sudo docker compose cp "$B/evolution.dump" postgres:/tmp/evolution.dump
sudo docker compose exec postgres sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists --no-owner --no-privileges /tmp/evolution.dump'
sudo docker compose exec postgres rm /tmp/evolution.dump

# Redis: load the RDB with AOF off, then switch AOF on live (README §3.5 explains why).
sudo docker compose stop redis
sudo docker run --rm -v baja_redis_data:/data alpine:3.22 sh -c 'rm -rf /data/appendonlydir /data/dump.rdb'
sudo docker run --rm -v baja_redis_data:/data -v "$B":/backup:ro alpine:3.22 cp /backup/evolution.rdb /data/dump.rdb
sudo docker run -d --name redis-import -v baja_redis_data:/data redis:8.10.2-alpine redis-server --appendonly no
sudo docker exec redis-import redis-cli CONFIG SET appendonly yes
sudo docker exec redis-import redis-cli INFO persistence | grep -E 'aof_rewrite_in_progress|aof_rewrite_scheduled|aof_last_bgrewrite_status'
```

Repeat the last command until both counters are `0` and the status is
`ok`, then:

```bash
sudo docker exec redis-import redis-cli SHUTDOWN
sudo docker rm redis-import
sudo docker compose up -d redis

# Instances volume: empty it, then unpack the backup.
sudo docker run --rm -v baja_evolution_instances:/instances alpine:3.22 sh -c 'rm -rf /instances/* /instances/.[!.]*'
sudo docker run --rm -v baja_evolution_instances:/instances -v "$B":/backup:ro alpine:3.22 tar -C /instances -xzf /backup/evolution_instances.tgz

sudo docker compose up -d evolution
sudo docker compose logs -f evolution     # instance loads; do NOT open the Manager / scan a QR
```

Then verify exactly as after the migration (README §4: state `open`, same
linked device on the phone, a test message both ways) and run
`sudo ./compose-smoke.sh`.

Messages received between the backup and the failure are not in the
restored Postgres; WhatsApp redelivers what the linked device had not
acknowledged yet, nothing more.

## D. A new VPS from scratch

1. README §0 and §2 (packages, directories, sysctl, swap, inbox mount,
   firewall), then put `.env` and `orchestrator.env` back from the password
   manager.
2. Copy the backup folder over the tailnet:
   `rsync -a <old-or-archive-host>:/var/backups/baja/<timestamp>/ /var/backups/baja/<timestamp>/`
   and check `sha256sum -c SHA256SUMS`.
3. `sudo docker compose pull`, `sudo docker compose create postgres redis evolution`,
   `sudo docker compose up -d caddy`.
4. Restore B, then C (with `docker compose up -d postgres` before its
   Postgres step), then A.
   A new VPS gets a new Tailscale IP, but every worker has the old one in
   `worker.json` (`orchestrator_url`, `tailnet_base_url`). Easiest: delete
   the old machine in the Tailscale admin console, then give the new one
   the old IPv4 (machine menu → *Edit machine IPv4*). Otherwise set the new
   `TAILSCALE_IP` in `.env` and edit both URLs in each worker's `worker.json`.
5. `sudo docker compose --profile orchestrator up -d`, README §6.2 step 2
   (webhook), `sudo ./compose-smoke.sh`.

## Keeping a copy off the VPS

The backups sit on the same disk as what they protect. Pull them to a
machine you control after the nightly run, over the tailnet (an admin
device may SSH to `tag:server`, `infra/tailnet/acl.hujson`), e.g. from
TrueNAS or João's desktop:

```bash
rsync -a --delete root@<vps-tailscale-ip>:/var/backups/baja/ /mnt/tank/backups/baja-vps/
```

## Practising a restore

Do drill A once before each event (EVENT_DAY.md, T-7) on a copy, without
stopping anything:

```bash
python3 /opt/baja/infra/vps/sqlite_backup.py restore "$B/bvp.sqlite3" /tmp/drill/bvp.sqlite3   # mkdir -p /tmp/drill first
rm -rf /tmp/drill
```

It prints the job count of the backup; it should match roughly what the
fleet page showed the night before.
